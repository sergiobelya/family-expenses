### Pending

- **Expense Domain Model** — Create the Expense bounded context with core domain entities: `Expense` (aggregate root with fields: family_id, author user_id, purchase date, store_id, original amount, original currency, type, soft-deletion state), `ExpenseAllocation` (category_id, amount in original currency). Value objects: `MoneyAmount` (wrapper around `moneyphp/money`, integrates with `CurrencyCode` VO, provides `allocate()` with largest-remainder rule per §6.4.1), `ExpenseId`, `AllocationId`. Domain events: `ExpenseCreated`, `ExpenseEdited`, `ExpenseDeleted`. Soft deletion with audit trail. `ExpenseConversion` and conversion rules are Phase 3.

- **Expense Repository and Persistence** — Implement `ExpenseRepositoryInterface` in Domain with CRUD operations scoped to `FamilyId`. Doctrine XML mappings for `expenses`, `expense_allocations`, and `expense_save_attempts` tables. Unique constraints, composite foreign keys enforcing family ownership of expense/store/category references, indexes (including family-scoped history by purchase date). Custom Doctrine Types for Value Objects, including `MoneyAmountType` for `MoneyAmount` ↔ PostgreSQL `NUMERIC` + `VARCHAR(3)` mapping. Repository methods: `findById`, `findByFamilyId`, `findExpenseById`, `save`, `softDelete`, `findAllocationsByExpenseId`, `findSaveAttemptByIdempotencyKey`, `saveSaveAttempt`, `markSaveAttemptComplete`, `markSaveAttemptUnknown`. Exclude soft-deleted expenses from normal queries. Support for atomic save of expense + allocations + audit snapshot + save attempt completion in one transaction (NFR §3, system_design §3). Validate allocation reconciliation in the domain/application layer: reject incomplete or non-positive allocation rows before persistence. `expense_conversions` table and conversion-related methods are Phase 3.

- **Add Expense Command and Handler** — Implement `AddExpenseCommand` and `AddExpenseHandler` in Application layer. Command carries: `FamilyId`, `UserId`, `StoreId`, `MoneyAmount`, `CategoryId[]` with allocation amounts, `DateTimeImmutable` purchase date. Handler: revalidates membership via `FamilyMembershipInterface` on every request, validates store/category family ownership, validates amount per currency precision (via `MoneyAmount` VO), validates date (not in future, not before min date), validates allocation sum equals total using `Money::allocate()` with largest-remainder rule, rejects incomplete or non-positive allocation rows. Before saving, moves the draft to `Saving` state and persists `ExpenseSaveAttempt` with idempotency key and immutable snapshot in PostgreSQL. Creates `Expense` aggregate with allocations, saves atomically with audit snapshot in the same transaction. On commit, marks the save attempt complete and the draft saved. On ambiguous outcome, retains `SaveUnknown` state for reconciliation by the same idempotency key. An unresolved save attempt must be reconciled before the draft can be replaced. Reuses the idempotency key to return the same committed expense after retries. Domain exceptions for validation failures mapped via `ErrorType` enum. Conversion handling and manual rate are Phase 3.

- **Edit and Delete Expense Handlers** — Implement `EditExpenseCommand`/`EditExpenseHandler` and `DeleteExpenseCommand`/`DeleteExpenseHandler`. Edit: author-only authorization, revalidation of all fields. Delete: author-only authorization, soft deletion, audit event. Conversion recalculation rules are Phase 3; Phase 2 edit/delete operates without currency conversion.

- **Expense Draft Infrastructure** — Implement expense draft storage and lifecycle management. Draft is scoped to `(user_id, family_id)` tuple, at most one nonterminal draft per tuple. States: Active, Paused, Saving, SaveUnknown, Saved, Discarded. Content: current step, awaiting_input type, return_step, card message ID, card revision, selected store, amount, currency, category allocations, category_customized flag, purchase date, idempototency key, timestamps. Active/Paused drafts expire 24 hours after last meaningful change. Draft storage in Redis (consistent with existing `UserInteractionStateRepository`). Idempotency key created with draft, persisted in `ExpenseSaveAttempt` before the first save transaction, and reused for every save attempt. Sequential processing of updates for one draft (lock or optimistic revision check). A family switch changes which draft is accessible; it does not move or rewrite a draft. An unresolved save attempt must be reconciled before the draft can be replaced. Conversion snapshot is Phase 3.

- **Add Expense Telegram Flow** — Implement the complete add expense wizard in Presentation layer following `add_expense.md` specification. States: AE-00 (Entry), AE-01 (Family context), AE-02 (Resume draft), AE-03 (Select store), AE-04 (Search stores), AE-05 (Draft paused: create store), AE-06 (Enter amount), AE-07 (More currencies), AE-08 (Select category), AE-09 (Split between categories), AE-10 (Review), AE-11 (Edit date), AE-13 (Saving), AE-14 (Success), AE-15 (Save error), AE-16 (Cancel confirmation), AE-17 (Expired draft), AE-18 (Stale callbacks). AE-12 (Manual exchange rate) is Phase 3. Use the one-card model with inline keyboards. Decompose into step classes with `AddExpenseStepInterface` (similar to FamilyCreationWizardHandler pattern). Shared utilities: card rendering, amount parsing, date parsing. Store/category detours pause the draft and redirect to existing Catalog flows. Rate parsing and conversion display are Phase 3.

- **Expense History and Search** — Implement expense history browsing and search following `expense_history.md` specification. States: HS-01 (History list), HS-02 (Search and filters), HS-03 (Expense details), HS-04 (Edit expense), HS-05 (Delete confirmation). Query handlers: `GetExpenseHistory`, `SearchExpenses`, `GetExpenseDetails`. Filters: store, category, date range, amount range. Phase 2 amount search compares original amounts without currency conversion; currency-aware amount search is Phase 3. Paginated results. Author-only edit/delete controls. Family-scoped reads with membership validation.
